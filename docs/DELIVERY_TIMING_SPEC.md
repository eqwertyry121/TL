# ТЗ: очередь и 30-минутные интервалы доставки

Статус: актуальное ТЗ DEV. Таймзона: `Europe/Belgrade`.

## 1. Цель

У доставки есть два понятных режима:

1. `Как можно скорее` — клиент видит только своё порядковое место в живой
   очереди. Автоматические минуты и точное время ему не обещаются.
2. `Ко времени` — клиент выбирает один реально свободный 30-минутный интервал
   текущего дня.

Каждый delivery-заказ занимает один интервал целиком. Два заказа не могут
получить одно время. ASAP и `Ко времени` используют один backend slot engine,
поэтому плановый заказ не может занять место, уже отданное текущей очереди.

Кухня отдельно назначает примерное время готовности и уведомляет клиента. Это
не новый status и не гарантированное время приезда курьера.

## 2. Ограничения

- один ресторан, одна кухня и один курьер;
- обычный polling, PostgreSQL — источник истины;
- без нового `PREPARING`, ручной приёмки, Redis, WebSocket/SSE и маршрутизации;
- delivery flow остаётся `NEW → OUT_FOR_DELIVERY → DELIVERED`;
- pickup flow и его интервалы не меняются;
- только текущий рабочий день, без предзаказа на будущие даты.

## 3. Правила времени

- минимальный отступ от server time — 30 минут;
- шаг — 30 минут;
- вместимость — ровно один заказ на интервал;
- последнее доступное время — 21:00 либо более ранний cutoff/закрытие;
- время округляется вверх к ближайшим `:00` или `:30`;
- занятый интервал не показывается как доступный;
- при одновременном submit последнее место защищается advisory lock и повторной
  проверкой внутри транзакции.

Пример в 13:00:

1. Первый ASAP-заказ получает внутренний интервал 13:30.
2. Свободные времена `Ко времени` начинаются с 14:00.
3. Следующий ASAP-заказ пропускает занятые плановые интервалы и занимает первый
   свободный.

## 4. Живая ASAP-очередь

- учитываются только delivery-заказы `NEW` с `delivery_time_mode=ASAP`;
- порядок — `created_at`, затем `id`;
- checkout показывает прогнозируемую позицию нового ASAP-заказа;
- активный ASAP-заказ показывает пересчитанную текущую позицию;
- `SCHEDULED`, `OUT_FOR_DELIVERY`, `DELIVERED` и `CANCELLED` в порядковый номер
  ASAP-очереди не входят;
- frontend не переводит позицию в `+30`, `+60` и точное время.

Внутренний `delivery_target_at` нужен только для общей вместимости и сортировки
кухни. Для ASAP он не отображается клиенту как обещание.

## 5. Client UX

В checkout один компактный блок `Когда доставить?` с двумя кнопками:

- `Как можно скорее` / `в порядке очереди`;
- `Ко времени` / `свободный интервал`.

### 5.1 Как можно скорее

Показываются:

- `Ваш заказ будет первым/вторым/... в очереди`;
- `После оформления кухня назначит время готовности и сообщит вам`.

В итоговом блоке: `Очередь кухни · №N`.

### 5.2 Ко времени

Показываются только доступные кнопки `14:00`, `14:30`, ... `21:00`. Подсказка:
`Свободное время. Один заказ занимает 30 минут.`

Без выбранного времени submit disabled. В итоговом блоке: `Ко времени · 14:00`.

Если слот заняли между просмотром и submit:

1. order не создаётся;
2. форма, корзина, contact и geo-проверка сохраняются;
3. frontend обновляет времена;
4. клиент выбирает другой свободный интервал отдельным нажатием.

Backend никогда не переносит заказ молча.

### 5.3 Активный заказ

- ASAP до оценки кухни — текущая позиция;
- SCHEDULED до оценки кухни — `Доставка ориентировочно к HH:MM`;
- после оценки кухни — время, назначенное кухней;
- после `ЗАКАЗ ГОТОВ` — обычный статус доставки.

## 6. Kitchen UX

Карточки сортируются по внутреннему `delivery_target_at`, затем `created_at`,
чтобы ASAP и плановые заказы находились в одном реальном порядке работы.

Кухня видит:

- для ASAP — `Очередь №N`;
- для SCHEDULED — `Ко времени HH:MM`;
- состав, оплату и остальные существующие данные.

Для оценки готовности остаётся одна кнопка `Назначить время` и один список
точного времени с шагом 5 минут. Второго dropdown, быстрых минут и действия в
`⋯` нет. ETA не меняет status и `kitchen_started_at`.

## 7. Backend и данные

Существующие поля:

- `delivery_time_mode`: `ASAP|SCHEDULED`;
- `delivery_requested_at`: выбор клиента только для SCHEDULED;
- `delivery_target_at`: атомарно занятый backend-интервал;
- `estimated_ready_at`: последняя оценка кухни.

Вычисляемые ответы:

- `asap.queue_position` для checkout;
- `kitchen_queue_position` только для активных ASAP-заказов.

`GET /api/v1/delivery/slots` возвращает ASAP и сетку интервалов. Client
показывает `queue_position` для ASAP и только `available=true` интервалы для
SCHEDULED. Чужие IDs, состав и точное количество заказов не возвращаются.

Calculation и create принимают одинаковые timing-поля; они входят в request
hash `Idempotency-Key`. Для SCHEDULED backend проверяет дату, шаг, границы дня и
вместимость. Создание под advisory lock повторно считает delivery и pickup
нагрузку выбранного интервала.

## 8. Уведомления

При создании не отправляется автоматический технический план ASAP.

После назначения кухней:

> Заказ #123 будет готов и передан курьеру ориентировочно к 18:20.

При изменении:

> Новое ориентировочное время готовности заказа #123 — 18:35.

Telegram failure не откатывает ETA; Mini App получает актуальное значение через
polling.

## 9. Admin

Параметры `30 минут минимум`, `30 минут шаг`, `1 заказ на интервал` и последнее
время `21:00` фиксированы правилами корректности и не редактируются. Admin может
только включить или выключить выбор времени.

В деталях заказа показываются mode, выбранное время для SCHEDULED, позиция для
ASAP, ETA кухни и фактическое `ready_at`.

## 10. Деградация

- slots API недоступен — scheduled submit недоступен, время не выдумывается;
- timing выключен — используется существующий обычный delivery flow;
- старый order без timing-полей показывает обычный status;
- отмена освобождает интервал;
- pickup продолжает работать по собственным правилам;
- SCHEDULED никогда не получает порядковый номер ASAP-очереди.

## 11. Acceptance criteria

1. После ASAP-заказа в 13:00, занявшего 13:30, первый SCHEDULED-вариант —
   14:00.
2. Один интервал принимает не более одного delivery/pickup заказа общей
   кухонной нагрузки.
3. Два конкурентных запроса не занимают одно время.
4. Занятый интервал не проходит server-side проверку и не переносится молча.
5. ASAP показывает только живую позицию без автоматических минут.
6. SCHEDULED не влияет на номер ASAP-очереди, но занимает общий интервал.
7. Kitchen видит `Очередь №N` или `Ко времени HH:MM` и одну кнопку ETA.
8. ETA не меняет business-status.
9. Pickup, `ЗАКАЗ ГОТОВ`, courier и one-active-order работают без изменений.
10. Нет horizontal overflow на телефоне и планшете `663 dp`.

## 12. Проверки

- PostgreSQL integration: ASAP 13:30 → SCHEDULED earliest 14:00;
- concurrent last-slot race;
- scheduled conflict и предложение следующего свободного;
- ASAP positions исключают SCHEDULED;
- cancel/ready освобождают нужные runtime списки;
- OpenAPI/generated types;
- client/kitchen/admin typecheck и production build;
- RU/SR/EN, узкий телефон и планшет `663 dp`;
- role, ownership, idempotency и version checks.
