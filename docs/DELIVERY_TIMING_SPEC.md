# ТЗ: живая очередь доставки и оценка готовности кухни

Статус: согласованное направление, до начала реализации требуется подтвердить
только числовые настройки из раздела 18.

Таймзона: `Europe/Belgrade`.

## 1. Зачем это нужно

Нужно решить две связанные задачи:

1. Клиент видит только своё понятное место в живой очереди кухни: первый,
   второй, третий и далее.
2. Кухня одним действием назначает конкретное примерное время готовности и
   сообщает его клиенту.

Frontend не переводит место очереди в `+30`, `+60` минут и не показывает
технический capacity-слот. Состав заказов разный, поэтому такой пересчёт создаёт
неоправданные ожидания. До решения кухни клиенту не сообщается конкретное время.

## 2. Ограничения текущего проекта

Решение сохраняет существующую простую архитектуру:

- один ресторан, одна кухня, один курьер;
- до примерно 50 заказов в день;
- Go modular monolith, PostgreSQL и обычный polling;
- без WebSocket/SSE, Redis, очередей маршрутизации и микросервисов;
- без геокодера, delivery zones, GPS-трекинга и расчёта времени дороги;
- без нового business-status `PREPARING`;
- основной автомат доставки остаётся
  `NEW → OUT_FOR_DELIVERY → DELIVERED`;
- `kitchen_started_at` остаётся внутренней отметкой `В ПРОЦЕССЕ`;
- существующее правило «один активный заказ на клиента» не меняется;
- самовывоз продолжает использовать собственные `pickup_at` и pickup-слоты.

Очередь и оценка кухни — дополнительные поля ответа, а не новые статусы.

## 3. Термины и смысл времени

### 3.1 Живая очередь

Клиент не выбирает конкретный час. До создания заказа backend возвращает
прогнозируемую позицию, после создания — текущую позицию среди активных
delivery-заказов `NEW`. Когда более ранний заказ покидает кухню, позиции
оставшихся заказов уменьшаются при следующем polling.

Технический capacity-слот остаётся внутренним ограничителем нагрузки. Его
`target_at`, `wait_minutes` и `queue_delay_minutes` не показываются клиенту и
не выдаются кухне за обещание.

### 3.2 Оценка кухни

После создания заказа кухня может уточнить время готовности одной из быстрых
кнопок. Эта оценка считается более актуальной, чем автоматический план
backend, но также остаётся приблизительной.

### 3.3 Что не вычисляется

Система не вычисляет ETA приезда к адресу и не прибавляет «время дороги»:

- нет данных о маршруте и пробках;
- нет геокодирования текстового адреса;
- курьер один и сам определяет порядок поездок.

Клиент видит отдельно:

- ориентир готовности/передачи курьеру;
- после `ЗАКАЗ ГОТОВ` — обычный статус `Заказ в доставке`.

## 4. Клиентский UX

### 4.1 Блок очереди

В checkout для `Доставка`, после адреса и до способа оплаты, показывается один
компактный информационный блок без выбора времени:

- `Очередь кухни`;
- `Ваш заказ будет первым/вторым/третьим в очереди`;
- `После оформления кухня назначит время готовности и сообщит вам`.

Для `Самовывоз` остаётся существующий обязательный выбор времени.

### 4.2 Правила позиции

- учитываются только delivery-заказы со статусом `NEW`;
- порядок — по фактическому времени создания, затем по ID для стабильности;
- checkout показывает прогнозируемую позицию нового заказа;
- активный заказ показывает пересчитанную текущую позицию;
- готовые, переданные курьеру, доставленные и отменённые заказы очередь кухни не
  занимают;
- позиция не превращается frontend-ом в минуты.

### 4.3 Проверка перед отправкой

В итоговом блоке checkout показывается только `Очередь кухни · №N`. Клиент не
выбирает время и не видит автоматически рассчитанные минуты.

### 4.4 Экран активного заказа

Для delivery-заказа в `NEW`:

- до оценки кухни — текущая позиция: `Ваш заказ второй в очереди`;
- после оценки кухни — `Кухня планирует закончить примерно к 18:20`;
- мелко — `Время примерное и может измениться`.

Когда более ранний заказ становится готов, позиция уменьшается при следующем
polling. Для `OUT_FOR_DELIVERY` блок очереди заменяется статусом доставки.

## 5. Расчёт живой очереди

Позиция вычисляется backend-ом и не хранится отдельным изменяемым полем:

1. учитываются только delivery-заказы в `NEW`;
2. сортировка — `created_at`, затем `id`;
3. checkout получает `COUNT(active) + 1`;
4. созданный заказ получает своё текущее место;
5. `OUT_FOR_DELIVERY`, `DELIVERED` и `CANCELLED` очередь не занимают.

Технические capacity-слоты остаются внутренней защитой backend и сохраняют
совместимость с уже созданными заказами. Их `target_at`, `wait_minutes` и
`queue_delay_minutes` нельзя показывать клиенту или кухне. Текущий client
создаёт delivery только в режиме `ASAP`; legacy `SCHEDULED` остаётся в API для
совместимости, но не предлагается в интерфейсе.

## 6. UX кухни

### 6.1 Карточка

Кухня сразу видит `Очередь №N`, состав и данные заказа. Автоматический план и
задержка слота не отображаются.

### 6.2 Одно действие времени

В карточке есть одна кнопка `Назначить время` (после назначения — `Изменить
время`). Она открывает один нижний список точного времени с шагом 5 минут на
ближайшие три часа. Второго выпадающего списка, быстрых минут и действия в `⋯`
нет.

Выбор времени:

- сразу сохраняет `estimated_ready_at` без confirm;
- уведомляет клиента после успешного сохранения;
- не меняет `fulfillment_status` и `kitchen_started_at`;
- доступен в колонках `НОВЫЕ` и `В ПРОЦЕССЕ`;
- перестаёт редактироваться после `ЗАКАЗ ГОТОВ`.

`ЗАКАЗ ГОТОВ` остаётся основной независимой кнопкой.

## 7. Уведомления клиенту

Первое назначение:

> Заказ #123 будет готов и передан курьеру примерно к 18:20. Время
> ориентировочное.

Обновление:

> Время готовности заказа #123 обновилось: ориентировочно к 18:35.

Автоматический технический план при создании не отправляется. Ошибка Telegram
не откатывает ETA: актуальные данные остаются доступны через polling.

## 8. Courier и Admin

Курьер может видеть последнюю оценку кухни, но не клиентское «желаемое время».
Сортировка `ОТВЕЗТИ` после готовности остаётся по `ready_at`.

Admin в деталях заказа видит текущую очередь, последнюю оценку кухни,
фактическое `ready_at` и историю изменения ETA. Технические capacity-настройки
могут оставаться в Admin, но не должны описываться как обещание клиенту.

## 9. Модель и API

- `kitchen_queue_position` — вычисляемое поле ответа order/summary;
- `GET /api/v1/delivery/slots` возвращает `asap.queue_position` для checkout;
- существующие timing-поля остаются для внутреннего capacity и обратной
  совместимости;
- client calculation/create всегда отправляет `delivery_time_mode=ASAP` и не
  отправляет `delivery_requested_at`;
- `POST /api/v1/kitchen/orders/{id}/estimate-ready` получает точный
  `estimated_ready_at` и `expected_version`;
- version, role и idempotency проверяются backend-ом.

Пример public-фрагмента:

```json
{
  "asap": {
    "queue_position": 3,
    "target_at": "2026-08-26T16:30:00Z",
    "wait_minutes": 70,
    "queue_delay_minutes": 30
  }
}
```

Frontend использует только `queue_position`. Остальные поля этого объекта
остаются внутренними и не отображаются человеку.

## 10. Конкурентность и деградация

- создание заказа сохраняет текущий idempotency flow;
- смена ETA использует version и отдельный idempotency key;
- конфликт вызывает refresh карточки без ложного успеха;
- старый order без queue/ETA показывает обычный статус;
- недоступность slots API не заставляет frontend выдумывать время;
- Telegram failure не мешает работе Mini App;
- pickup flow и обязательный выбор времени самовывоза не меняются.

## 11. Что намеренно не делаем

- клиентский выбор времени доставки;
- перевод очереди в `0, 0, +30, +30, +60, +60`;
- гарантированное время приезда;
- расчёт дороги, карту, маршрутизацию и пробки;
- новый fulfillment status или принятие заказа кухней;
- автоматическую оценку сложности блюд;
- новый сервис, Redis, WebSocket/SSE.

## 12. Acceptance criteria

1. Checkout показывает прогнозируемое порядковое место без минут и точного
   времени.
2. Активный заказ показывает пересчитанную живую позицию.
3. После готовности более раннего заказа позиции оставшихся уменьшаются.
4. Клиент видит точное примерное время только после решения кухни.
5. Kitchen видит одну кнопку и один список точного времени.
6. В kitchen нет автоматического плана, queue delay и второго time picker.
7. ETA не меняет status или внутреннюю отметку `В ПРОЦЕССЕ`.
8. `ЗАКАЗ ГОТОВ`, pickup и courier flow работают без изменений.
9. Client не получает данные или состав чужих заказов.
10. Нет horizontal overflow на телефоне и планшете `663 dp`.

## 13. Проверки перед сдачей

- backend integration: позиции 1..N и их уменьшение после `ЗАКАЗ ГОТОВ`;
- contract/OpenAPI: `queue_position` и `kitchen_queue_position`;
- client typecheck: нет выбора scheduled и отображения delay;
- kitchen typecheck: ровно один exact-time picker;
- RU/SR/EN, polling, narrow phone и tablet `663 dp`;
- ETA idempotency/version/status conflict и notification retry;
- pickup regression и one-active-order regression.
