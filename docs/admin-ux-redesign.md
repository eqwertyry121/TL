# UX-ТЗ: переработка Admin Mini App

Статус: готово к реализации.

Основание: `docs/00_MASTER_SPEC.md` и `docs/stages/04_ADMIN.md`.

## 1. Цель

Сделать админку рабочим инструментом владельца небольшого ресторана, а не
набором технических форм. Любое ежедневное действие должно находиться за
один-два нажатия, редкие настройки не должны мешать контролю заказов.

Главные сценарии по приоритету:

1. понять, принимаются ли сейчас заказы;
2. увидеть активные заказы и быстро открыть нужный;
3. остановить или возобновить приём заказов;
4. скрыть блюдо, изменить цену или добавить блюдо;
5. проверить результат дня;
6. изменить график или настройку;
7. управлять сотрудниками и смотреть журнал действий.

Новых бизнес-функций это ТЗ не добавляет. Backend остаётся одним Go-сервисом,
данные — в PostgreSQL, обновление — polling.

## 2. Основные проблемы текущего UX

- восемь разделов показаны как одинаково важные;
- `Сотрудники` находятся раньше ежедневных разделов `График` и `Аналитика`;
- на мобильном вся навигация превращается в длинную горизонтальную ленту;
- в шапке постоянно показан технический `ID создателя` и переключатель ролей;
- на экранах много постоянных пояснений, которые владелец прочитает один раз;
- каждая карточка заказа занимает слишком много высоты;
- редкие и опасные действия стоят рядом с обычными;
- категории и блюда одновременно занимают две большие колонки;
- SR/EN, GPS-параметры, версии записей и другие редкие поля всегда находятся
  перед глазами;
- приложение при входе запрашивает все разделы сразу, а после любого изменения
  перезагружает всё;
- ошибка одного раздела способна ухудшить работу всей админки;
- используются browser `prompt`/`confirm`, которые неудобны в Telegram WebView.

## 3. Новая информационная архитектура

### 3.1 Порядок разделов

Порядок одинаковый во всём приложении:

1. `Главная`;
2. `Заказы`;
3. `Меню`;
4. `График`;
5. `Аналитика`;
6. `Настройки`;
7. `Журнал действий`;
8. `Сотрудники`.

`Сотрудники` — последний пункт. Он нужен редко и не должен находиться среди
ежедневных действий.

### 3.2 Навигация на телефоне

Внизу закреплена панель из четырёх пунктов:

- `Главная`;
- `Заказы`;
- `Меню`;
- `Ещё`.

У `Заказы` показывается badge с количеством активных заказов. Badge отсутствует,
если активных заказов нет.

`Ещё` открывает нижний лист на весь доступный экран:

1. `График`;
2. `Аналитика`;
3. `Настройки`;
4. `Журнал действий`;
5. `Сотрудники`.

Текущий редкий раздел отмечается активным внутри `Ещё`. Панель учитывает
`safe-area-inset-bottom` и не перекрывает контент или основную кнопку формы.

### 3.3 Навигация на планшете и компьютере

Слева находится компактная боковая панель. Пункты сгруппированы:

- `Работа`: Главная, Заказы, Меню;
- `Управление`: График, Аналитика;
- `Система`: Настройки, Журнал действий, Сотрудники.

Названия групп визуально тихие и не являются кнопками. `Сотрудники` остаются
самым нижним пунктом. На узком планшете sidebar может сворачиваться до иконок,
но tooltip/подпись появляется по нажатию или наведению.

### 3.4 Шапка

Шапка содержит только:

- название текущего раздела;
- компактный статус ресторана: `Принимаем заказы` или `Приём остановлен`;
- avatar ADMIN или кнопка `⋯`.

Убрать из постоянной шапки:

- `ID создателя: 1048084234`;
- длинные подзаголовки;
- текстовую кнопку `Обновить`;
- переключатель ролей владельца.

Ручное обновление становится иконкой внутри `⋯`. Переключение ролей владельца
переезжает в `Ещё`/профиль и показывается только Telegram ID владельца.

## 4. Правила текста

Админка должна объяснять действие интерфейсом, а не абзацами.

### 4.1 Лимиты

- заголовок экрана: 1–3 слова;
- заголовок карточки: до 4 слов;
- подпись поля: 1–3 слова;
- постоянная подсказка: не более одной короткой строки;
- empty state: одна строка и, если нужно, одна кнопка;
- подтверждение опасного действия: заголовок, одно предложение, две кнопки;
- toast об успехе: 2–5 слов.

### 4.2 Что не показывать постоянно

- версии записей (`v1`, `v2`);
- внутренние UUID;
- ID владельца;
- технические причины API;
- правила работы, уже очевидные из полей;
- объяснение, что старые заказы сохраняют старую цену;
- координаты, TTL и точность GPS на обычном экране;
- сообщения `Ошибок нет` отдельной большой карточкой.

Техническая информация доступна в `Подробнее`, `Расширенные настройки` или
журнале действий.

### 4.3 Тон текста

Использовать короткие прямые формулировки:

- `Остановить приём`, а не `Остановить приём заказов на текущий момент`;
- `Скрыть блюдо`, а не `Убрать блюдо из клиентского меню`;
- `Заказы до 21:00`, а не длинное описание cutoff;
- `Не удалось сохранить. Повторить`, а не код backend-ошибки;
- `Нет активных заказов`, а не пустая таблица.

Термины `cash`, `TTL`, `provider`, `version`, `archive` не использовать в
обычном русскоязычном интерфейсе. Писать `наличные`, `срок подтверждения`,
`платёжный сервис`, `архив`.

## 5. Общий каркас экранов

### 5.1 Одна главная задача

На экране или в открытой форме должна быть одна визуально главная кнопка.
Второстепенные действия — нейтральные. Опасные действия находятся в `⋯` и
показываются винно-красным только после открытия меню.

### 5.2 Списки вместо больших карточек

Заказы, блюда, сотрудники и события показываются компактными строками. Строка
содержит только данные для выбора нужной записи. Полные данные открываются после
нажатия.

Минимальная высота touch target — 44 px. Горизонтального скролла контента нет.

### 5.3 Детали

На телефоне детальная запись открывается отдельным внутренним экраном. Кнопка
назад Telegram и системный жест возвращают в список на прежнюю scroll-позицию.

На ширине от 900 px используется схема `список + детали`: список слева, детали
выбранной записи справа. Открытие деталей не прокручивает страницу наверх.

### 5.4 Формы

- поля разбиты на короткие смысловые блоки;
- обязательные поля идут первыми;
- RU открыт сразу;
- SR-Latn и EN находятся в блоке `Переводы` и свёрнуты по умолчанию;
- редкие поля находятся в `Дополнительно`;
- кнопка `Сохранить` закреплена снизу и активна только при изменениях;
- рядом доступна нейтральная `Отмена`;
- при выходе с несохранёнными изменениями появляется собственный диалог;
- ошибка показывается рядом с проблемным полем;
- после успеха форма закрывается или остаётся открытой согласно явному действию,
  scroll-позиция списка сохраняется.

Browser `prompt`, `alert` и `confirm` не использовать.

### 5.5 Состояния

Каждый раздел обязан иметь собственные:

- skeleton загрузки;
- empty state;
- inline error с кнопкой `Повторить`;
- offline state `Нет связи`;
- состояние сохранения без повторного нажатия;
- success toast.

Ошибка `Аналитики` не должна ломать `Главную`, `Заказы` или навигацию.

## 6. Экран `Главная`

Главная отвечает только на вопросы: работает ли ресторан, что происходит с
заказами и требуется ли внимание владельца.

Порядок блоков:

1. состояние приёма заказов;
2. активные заказы;
3. результат сегодня;
4. проблемы, только если они есть;
5. быстрые действия.

### 6.1 Состояние ресторана

Одна компактная карточка:

- зелёная точка + `Принимаем заказы`;
- или терракотовая точка + `Приём остановлен`;
- вторая строка: `Заказы до 21:00` либо краткая реальная причина;
- основная кнопка: `Остановить приём` / `Возобновить приём`.

При остановке показать диалог:

- заголовок: `Остановить приём?`;
- текст: `Новые заказы будут недоступны. Активные заказы останутся в работе.`;
- кнопки: `Остановить` и `Отмена`.

После возобновления интерфейс обязан показать фактическое состояние backend.
Если по графику сейчас закрыто, текст: `Приём выключен по графику`, а не ложное
`Принимаем заказы`.

### 6.2 Активные заказы

Две нажимаемые компактные карточки:

- `На кухне` — количество `NEW`;
- `В доставке` — количество `OUT_FOR_DELIVERY`.

Нажатие открывает `Заказы` с готовым фильтром. Ноль показывается спокойно, без
яркого badge.

### 6.3 Сегодня

Две метрики в одной строке:

- `Заказы`;
- `Выручка`.

Не дублировать здесь доставленные, отменённые и средний чек — они находятся в
`Аналитике`.

### 6.4 Требует внимания

Блок вообще не рендерится, если проблем нет. При наличии ошибок показывается
до трёх строк: короткая проблема, время и действие `Открыть`. Остальные доступны
по `Показать все`.

### 6.5 Быстрые действия

Не более трёх:

- `Добавить блюдо`;
- `Изменить график`;
- `Открыть аналитику`.

## 7. Экран `Заказы`

### 7.1 Фильтры

Вверху сегменты с количеством:

- `Активные` — `NEW` + `OUT_FOR_DELIVERY`, выбран по умолчанию;
- `Новые`;
- `В доставке`;
- `История` — `DELIVERED` + `CANCELLED`.

Поиск свёрнут в одну строку с placeholder `Номер, клиент или телефон`.
Дата и дополнительные статусы находятся в кнопке `Фильтры`. Отдельную большую
строку пагинации сверху не показывать.

### 7.2 Строка заказа

Компактная строка высотой примерно 76–92 px:

- `#104` и время;
- имя или `@username` клиента;
- одна строка состава: `Хинкали ×6 · Лобио ×1`;
- сумма;
- статусный badge.

Адрес, телефон, геопроверку и все кнопки не показывать в списке. Новый заказ
можно выделить тонкой винной полосой слева, но не большой цветной заливкой.

### 7.3 Детали заказа

Порядок:

1. номер, статус, время;
2. состав и суммы;
3. клиент — кликабельный `@username`, телефон;
4. адрес;
5. способ и статус оплаты;
6. комментарий клиента, только если есть;
7. история, свёрнутая в `История заказа`.

Обычные действия рядом с данными:

- нажать username — открыть Telegram ЛС;
- нажать телефон — позвонить;
- нажать адрес — скопировать.

Редкие действия находятся в `⋯`:

- исправить контакт и адрес;
- вернуть на кухню;
- повторить сообщение клиенту;
- повторить сообщение курьеру;
- добавить заметку;
- отменить заказ.

Отмена и возврат на кухню открывают собственный диалог с обязательной причиной.
Действия, невозможные для текущего статуса, не показываются.

## 8. Экран `Меню`

### 8.1 Верхний уровень

Использовать переключатель:

- `Блюда` — выбран по умолчанию;
- `Категории`.

Справа одна кнопка `+ Добавить`. Она создаёт блюдо или категорию согласно
выбранному сегменту. `Архив` находится в `⋯`, а не отдельным постоянным checkbox.

### 8.2 Список блюд

Над списком горизонтальные chips категорий: `Все`, затем активные категории.

Строка блюда:

- фото 48–56 px;
- название;
- категория одной короткой строкой;
- цена;
- переключатель `В меню`.

Никаких версий, длинного описания, минимального количества и кнопок
`Редактировать / В архив / Удалить` в строке. Нажатие на строку открывает
редактор. Архивирование находится в `⋯` редактора.

Переключение `В меню` выполняется сразу, показывает короткий progress и при
ошибке возвращает прежнее значение.

### 8.3 Список категорий

Строка:

- название;
- количество блюд;
- статус `В меню`/`Скрыта`;
- drag handle на desktop или кнопки порядка внутри редактора на mobile.

Нажатие открывает редактор категории. Скрытие категории предупреждает, что
клиенты перестанут видеть все её блюда.

### 8.4 Редактор блюда

Блоки в порядке:

1. фото;
2. название RU;
3. описание RU;
4. цена;
5. категория;
6. минимум штук;
7. вес/порция;
8. `Показывать в меню`;
9. свёрнутый блок `Переводы`;
10. свёрнутый блок `Аллергены и порядок`;
11. компактный preview карточки клиента;
12. `⋯` с архивированием.

Не показывать текстовое поле пути/URL фотографии. ADMIN видит только фото,
`Заменить` и `Удалить фото`.

При изменении цены confirmation появляется только при сохранении:
`Цена изменится с 690 на 720 RSD.`

## 9. Экран `График`

Убрать два постоянных абзаца с описанием правил.

Каждый день — одна компактная строка:

- `Пн`;
- `Выходной` или `13:00–22:00`;
- подпись `заказы до 21:00` только для рабочего дня;
- switch `Рабочий день`.

Нажатие на рабочий день открывает нижний лист с тремя полями:

- `Открытие`;
- `Заказы до`;
- `Закрытие`.

Изменение switch сохраняется сразу с progress на конкретной строке. Изменение
времени сохраняется кнопкой `Сохранить`. Внизу одна короткая подпись:
`Время Нови-Сада`.

## 10. Экран `Аналитика`

Вверху сегменты:

- `Сегодня`;
- `7 дней`;
- `Месяц`.

Основные метрики:

- `Выручка` — визуально главная;
- `Заказы`;
- `Средний чек`;
- `Отменено`.

`Доставлено` не нужно отдельной равнозначной карточкой: показать небольшой
строкой рядом с количеством заказов.

Ниже:

- `Популярные блюда` — 5 строк с названием, количеством и выручкой;
- `По дням` — компактные строки, на широком экране допустим простой bar chart;
- способы оплаты показывать только если реально используется больше одного.

Если данных нет, показать `За этот период заказов нет`. Не рисовать пять нулевых
карточек. Время формирования — мелко внизу. `Скачать CSV` находится в `⋯`.

## 11. Экран `Настройки`

Не использовать одну длинную форму. Настройки разбиты на карточки:

1. `Заказы` — максимум одного блюда и длина комментария;
2. `Поддержка` — Telegram, телефон, условия;
3. `Наличные` — включены ли наличные и нужна ли геопроверка;
4. `Способы оплаты` — только доступные backend способы;
5. `Расширенные` — координаты ресторана, радиус, срок и точность проверки.

На главном экране каждой карточки показывать текущие значения и кнопку
`Изменить`. Редактирование открывается отдельно, сохранение действует только на
эту карточку.

Технические GPS-поля в `Расширенных` подписать человечески:

- `Радиус проверки`;
- `Срок подтверждения`;
- `Допустимая погрешность`.

Широту и долготу показывать только внутри `Координаты ресторана`.

Не показывать постоянные предупреждения про бесплатную доставку, crypto sandbox
и несохранение точных координат. Актуальная важная информация размещается
одной строкой внутри соответствующего редактора.

## 12. Экран `Журнал действий`

Строка события:

- человеческое действие: `Анна изменила цену Лобио`;
- время;
- причина, если была.

Технический target type, role и raw before/after в списке не показывать.
Нажатие раскрывает безопасные подробности. Фильтры: `Все`, `Заказы`, `Меню`,
`Настройки`. Пустое состояние: `Изменений пока нет`.

## 13. Экран `Сотрудники`

Раздел находится последним в навигации.

Список группируется по человеку, а не по отдельной строке на каждую роль:

- имя/метка;
- Telegram ID мелким текстом;
- chips ролей `Админ`, `Кухня`, `Курьер`;
- статус `Активен`/`Отключён`.

Нажатие открывает редактор. Добавление сотрудника:

1. Telegram ID;
2. понятное имя;
3. выбор одной или нескольких ролей;
4. `Добавить`.

Отключение находится в `⋯` и требует подтверждения. Интерфейс заранее объясняет
только реальные ограничения: нельзя отключить последнего ADMIN и нельзя иметь
двух активных курьеров. Эти сообщения показываются при соответствующем действии,
а не постоянным текстом на странице.

Если backend продолжает хранить одну запись на пару `user + role`, frontend
сам группирует записи по `telegram_user_id`. Изменение нескольких ролей отправляет
несколько существующих команд последовательно и показывает единый результат.

## 14. Визуальный стиль

Админка использует существующую ресторанную палитру, но выглядит спокойнее
клиентского приложения:

- фон — тёплый кремовый;
- поверхности — молочные;
- основное действие — глубокий винный;
- успешный статус — оливковый;
- опасность — терракотовый;
- золото — только маленький декоративный акцент;
- основной текст — тёмно-шоколадный.

Не использовать декоративные градиенты на каждой карточке, движущийся фон,
сильный blur и большие тени. Операционный интерфейс должен быстро сканироваться
и плавно работать в Telegram WebView.

Шрифт display допустим только для названия ресторана и крупных заголовков.
Таблицы, формы, суммы и кнопки используют хорошо читаемый sans-serif. Цвет не
является единственным признаком состояния: рядом всегда есть иконка или текст.

## 15. Адаптивность

### Телефон, 320–599 px

- одна колонка;
- нижняя навигация;
- детали отдельным экраном;
- формы и диалоги как full-height bottom sheet;
- sticky save над нижней навигацией;
- не более двух маленьких метрик в строке;
- поля времени могут стоять по два или по одному, без обрезки;
- минимальный текст 14 px, основной 16 px, touch target 44 px.

### Планшет, 600–899 px

- нижняя навигация либо компактный sidebar в зависимости от доступной ширины;
- две колонки только для коротких метрик;
- списки остаются одной колонкой;
- формы могут использовать две колонки для коротких полей.

### Desktop, от 900 px

- sidebar;
- контент ограничен примерно 1280 px и не растягивается бесконечно;
- `список + детали` для заказов и меню;
- аналитика и главная используют сетку;
- формы не шире комфортной области чтения.

Обязательно проверить Telegram Android, Telegram iOS, Telegram Desktop и
обычный desktop browser.

## 16. Загрузка данных и устойчивость

### 16.1 Не загружать всё сразу

После авторизации загрузить только `dashboard` и минимум данных, нужных для
каркаса. Остальные разделы загружаются при первом открытии и кэшируются на время
сессии:

- `Заказы` — при открытии раздела;
- `Меню` — при открытии раздела;
- `Аналитика` — только при открытии или смене периода;
- `Сотрудники` и `Журнал` — только при открытии.

### 16.2 Обновлять только затронутые данные

- day off обновляет dashboard/settings/runtime;
- изменение блюда обновляет menu;
- действие с заказом обновляет выбранный заказ, список и dashboard counters;
- изменение сотрудника обновляет staff;
- изменение графика обновляет schedule/runtime.

После любой мутации не делать восемь параллельных запросов.

### 16.3 Polling

- `Главная` и открытый список активных заказов: примерно раз в 10 секунд;
- скрытая вкладка не polling-ится;
- после возврата приложения из background текущий раздел обновляется сразу;
- ручное обновление доступно в `⋯` и обновляет только текущий раздел.

### 16.4 Изоляция ошибок

- отдельный Error Boundary на уровень раздела;
- API-массивы нормализуются: `null` превращается в `[]` на границе клиента;
- один сломанный ответ не очищает уже показанные корректные данные;
- технический request ID доступен через `Подробнее`, но не мешает основному
  сообщению.

## 17. Реализация по этапам

### UX-A — каркас и навигация

- новая mobile bottom navigation и desktop sidebar;
- новый порядок разделов;
- `Ещё` и перенос role switch;
- компактная шапка без ID владельца;
- внутренний router/back behavior;
- базовые skeleton/error/toast/dialog/bottom-sheet компоненты.

Результат: все существующие разделы доступны в новой структуре, функции ещё не
переработаны внутри.

### UX-B — Главная и Заказы

- компактная Главная;
- кликабельные counters;
- фильтр `Активные` по умолчанию;
- компактный список заказов;
- отдельные детали заказа;
- действия в `⋯` и собственные dialogs вместо prompt/confirm;
- polling только видимого раздела.

Результат: ежедневный контроль ресторана удобен с телефона одной рукой.

### UX-C — Меню

- сегменты `Блюда / Категории`;
- фильтрация блюд по категории;
- быстрый visibility switch;
- новый редактор с RU, свёрнутыми переводами и preview;
- архив внутри `⋯`;
- убрать технический photo path и версии.

Результат: скрыть блюдо можно одним нажатием, изменить или добавить — без поиска
по длинной странице.

### UX-D — График, Аналитика и Настройки

- компактные строки графика;
- аналитика с правильной визуальной иерархией;
- настройки по карточкам и отдельное сохранение секций;
- технические GPS-параметры в `Расширенных`.

Результат: редкие формы не перегружают ежедневную работу.

### UX-E — Журнал, Сотрудники и полировка

- человеческий журнал;
- группировка сотрудников по Telegram user;
- финальные empty/error/offline states;
- responsive QA;
- keyboard/focus/accessibility QA;
- performance проверка в Telegram WebView.

Результат: вся админка соответствует этому ТЗ.

## 18. Acceptance criteria

- На телефоне всегда видны `Главная`, `Заказы`, `Меню`, `Ещё`; горизонтальной
  ленты из восьми вкладок нет.
- `Сотрудники` — последний пункт внутри `Ещё` и sidebar.
- На Главной ADMIN за 2–3 секунды понимает состояние ресторана, активные заказы
  и результат дня.
- Остановить приём можно максимум за два нажатия с понятным подтверждением.
- Открыть активный заказ можно максимум за два нажатия после входа.
- В списке заказов на экране обычного телефона помещается не менее четырёх строк
  без потери номера, статуса и состава.
- Скрыть доступное блюдо можно одним нажатием из списка меню.
- Добавление/редактирование блюда не показывает SR/EN и технические поля, пока
  ADMIN сам их не раскрыл.
- Ни один основной экран не содержит постоянного поясняющего абзаца длиннее
  одной строки.
- В интерфейсе нет UUID, version, raw API codes, raw JSON и ID владельца.
- Опасные действия не стоят рядом с основной кнопкой и требуют явного
  подтверждения/причины.
- Ошибка одного раздела не ломает каркас и остальные разделы.
- После изменения перезагружаются только затронутые данные.
- Scroll-позиция списка сохраняется после просмотра/редактирования записи.
- Нет browser prompt/alert/confirm.
- Нет горизонтального скролла на ширине 320 px.
- Все интерактивные элементы имеют touch target не меньше 44×44 px.
- Основные сочетания текста соответствуют WCAG AA.
- Интерфейс проверен на Android, iOS, Telegram Desktop и desktop browser.

## 19. Что не делать

- не добавлять новые роли;
- не добавлять склад, stop-list кухни, филиалы или нескольких курьеров;
- не превращать Главную в BI-dashboard;
- не добавлять графики ради декора;
- не делать drag-and-drop обязательным для мобильного;
- не помещать все настройки в одну длинную форму;
- не показывать редкие действия постоянно;
- не использовать модальные окна для обычной навигации;
- не запускать полный reload всех admin endpoint после каждого действия;
- не менять backend status произвольным dropdown.
