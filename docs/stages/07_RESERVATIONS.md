# Этап 7 — бронирование столиков в основной Mini App

## Цель

Заменить основную клиентскую вкладку `Поддержка` на `Бронь стола` и дать клиенту
возможность забронировать стол через основной `@TakoLako_main_bot` и ту же
Mini App. Старый restobot продолжает работать штатно и не изменяется.

## Правила первой версии

- Телеп, `Koste Abraševića 49`: два стола, каждый на 1–5 гостей;
- Подбара, `Temerinska 44`: общая вместимость 21 гость, без назначения номера стола;
- бронь длится два часа;
- начало слота — каждый час с 13:00 до 21:00 включительно;
- доступны ближайшие семь календарных дней, включая понедельник;
- один Telegram user может иметь только одну будущую активную бронь;
- на Телепе номер стола назначает backend автоматически;
- на Подбаре backend считает занятые места на каждый час броней;
- клиент может отменить свою бронь;
- ADMIN видит точку каждой брони, может её отменить и одним нажатием
  закрыть/открыть новые брони каждой точки, не меняя существующие;
- история не удаляется: отменённая бронь остаётся в PostgreSQL.

## Client UX

Основная навигация: `Меню · Корзина · Заказы · Бронь стола`.

Экран `Бронь стола` сначала предлагает выбрать точку и показывает её адрес.
После выбора доступны количество гостей и свободные часы. По умолчанию выбраны
два гостя: на Телепе количество выбирается кнопками `1–5`, на Подбаре — списком
`1–21`. Клиенту не предлагается выбирать номер стола.
Даты выводятся компактным горизонтальным списком. После выбора даты интерфейс
показывает только список свободного времени этого дня, а не карточки всех семи
дней одновременно.
Основной сценарий после открытия экрана:

1. выбрать точку;
2. нажать свободное время;
3. нажать `ЗАБРОНИРОВАТЬ` в компактном подтверждении.

Нет календаря, выбора номера стола, анкеты и обязательного телефона. Если
активная бронь уже есть, вместо формы показывается её карточка и кнопка
`ОТМЕНИТЬ БРОНЬ`. Активная бронь оформляется одной цельной карточкой: дата,
интервал времени и количество гостей читаются отдельно. Раздельные цветные
бейджи начала и окончания времени не используются.

Поддержка переносится в компактный блок `⋯` в клиентской шапке. Юридические
страницы остаются доступны по прямым маршрутам. Меню `⋯` рендерится верхним
слоем страницы и не может оказаться под вкладками шапки.

Закрытие приёма заказов не запрещает будущую бронь: из плашки выходного можно
перейти в `Бронь стола`, при этом заказ еды остаётся заблокирован.

## Backend

PostgreSQL является источником истины. Создание брони выполняется транзакцией:

- блокируется строка точки, чтобы проверка мест и переключение приёма были
  согласованы с конкурентным созданием броней;
- повторно проверяется активная бронь клиента;
- на Телепе выбирается первый свободный стол;
- на Подбаре отдельно для каждого часа интервала проверяется, что сумма гостей
  с новой бронью не превысит 21;
- проверяется пересечение двухчасового интервала;
- создаётся бронь и уведомления;
- `Idempotency-Key` предотвращает повтор от двойного нажатия.

Frontend не отправляет номер стола и не определяет доступность самостоятельно.

## API

- `GET /reservations/availability?guests=2`;
- `GET /reservations/locations`;
- `GET /reservations/mine`;
- `POST /reservations` с `Idempotency-Key`;
- `POST /reservations/{id}/cancel`;
- `GET /admin/reservations`;
- `POST /admin/reservations/{id}/cancel`;
- `PUT /admin/reservation-locations/{code}` открывает или закрывает приём броней.

## Admin UX

Раздел `Брони` находится рядом с заказами. День выбирается одним компактным
выпадающим списком: внутри видны ближайшие семь дней, дата и количество активных
броней. Сверху раздела находится переключение приёма броней каждой точки, с её
названием и адресом. Дни не размещаются одной горизонтальной строкой и не ломают мобильную
вёрстку. На экране одновременно открыт только выбранный день: время, стол,
клиент и количество гостей. Единственное основное действие — `ОСВОБОДИТЬ СТОЛ`.
В рабочем списке показываются только активные брони. Отменённые брони сразу
исчезают из интерфейса, но остаются в PostgreSQL для истории и аудита.

У каждого owner поверх любой открытой вкладки Admin Mini App появляется
постоянное уведомление о новой брони: стол, время, дата и количество гостей.
Уведомление обновляется обычным polling, закрывается вручную, а нажатие по нему
открывает нужный день раздела `Брони`. Старые брони при первом запуске приложения
не показываются как новые.

## Telegram

Основной bot webhook обрабатывает `/start` и `/book` и показывает Web App
кнопки `Заказать еду` и `Забронировать стол`. При создании брони основной бот
уведомляет клиента и каждого owner через существующую очередь уведомлений.
Owner получает короткое сообщение со столом, датой, временем, количеством гостей
и Telegram-именем клиента. Отмена клиентом также отправляется каждому owner.

Старый restobot:

- не останавливается;
- не переключается в redirect-режим;
- не использует новые таблицы;
- продолжает обслуживать свои брони независимо.

## Acceptance criteria

- `Поддержка` отсутствует в четырёх основных клиентских вкладках;
- `Бронь стола` открывается из основной навигации;
- поддержка доступна через дополнительное меню;
- свободное время считается backend;
- два одновременных запроса не занимают один стол и не превышают 21 место на Подбаре;
- закрытие одной точки блокирует только новые брони этой точки, повторное открытие их разрешает;
- один пользователь не создаёт две будущие активные брони;
- клиент и ADMIN могут отменить бронь;
- ADMIN видит ближайшие брони;
- каждый owner получает Telegram-сообщение о новой брони;
- owner видит новую бронь поверх любой вкладки Admin Mini App;
- основной бот открывает экран бронирования;
- старый `restobot.service` остаётся запущен и не изменён.
