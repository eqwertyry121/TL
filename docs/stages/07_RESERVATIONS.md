# Этап 7 — бронирование столиков в основной Mini App

## Цель

Заменить основную клиентскую вкладку `Поддержка` на `Бронь стола` и дать клиенту
возможность забронировать стол через основной `@TakoLako_main_bot` и ту же
Mini App. Старый restobot продолжает работать штатно и не изменяется.

## Правила первой версии

- два стола;
- каждый стол принимает от 1 до 5 гостей;
- бронь длится два часа;
- начало слота — каждый час с 13:00 до 20:00;
- доступны ближайшие семь календарных дней;
- понедельник закрыт;
- один Telegram user может иметь только одну будущую активную бронь;
- номер стола назначает backend автоматически;
- клиент может отменить свою бронь;
- ADMIN видит брони и может освободить стол;
- история не удаляется: отменённая бронь остаётся в PostgreSQL.

## Client UX

Основная навигация: `Меню · Корзина · Заказы · Бронь стола`.

Экран `Бронь стола` сразу показывает дни и свободные часы. Количество гостей по
умолчанию равно двум и выбирается одной из пяти явных кнопок `1 · 2 · 3 · 4 · 5`.
Основной сценарий после открытия экрана:

1. нажать свободное время;
2. нажать `ЗАБРОНИРОВАТЬ` в компактном подтверждении.

Нет календаря, выбора номера стола, анкеты и обязательного телефона. Если
активная бронь уже есть, вместо формы показывается её карточка и кнопка
`ОТМЕНИТЬ БРОНЬ`.

Поддержка переносится в компактный блок `⋯` в клиентской шапке. Юридические
страницы остаются доступны по прямым маршрутам.

Закрытие приёма заказов не запрещает будущую бронь: из плашки выходного можно
перейти в `Столик`, при этом заказ еды остаётся заблокирован.

## Backend

PostgreSQL является источником истины. Создание брони выполняется транзакцией:

- блокируется конкурентный выбор столов;
- повторно проверяется активная бронь клиента;
- выбирается первый свободный стол;
- проверяется пересечение двухчасового интервала;
- создаётся бронь и уведомления;
- `Idempotency-Key` предотвращает повтор от двойного нажатия.

Frontend не отправляет номер стола и не определяет доступность самостоятельно.

## API

- `GET /reservations/availability?guests=2`;
- `GET /reservations/mine`;
- `POST /reservations` с `Idempotency-Key`;
- `POST /reservations/{id}/cancel`;
- `GET /admin/reservations`;
- `POST /admin/reservations/{id}/cancel`.

## Admin UX

Раздел `Брони` находится рядом с заказами. Он показывает ближайшие брони по
дням: время, стол, клиента и количество гостей. Единственное основное действие
— `ОСВОБОДИТЬ СТОЛ`.

## Telegram

Основной bot webhook обрабатывает `/start` и `/book` и показывает Web App
кнопки `Заказать еду` и `Забронировать стол`. При создании брони основной бот
уведомляет клиента и ADMIN через существующую очередь уведомлений.

Старый restobot:

- не останавливается;
- не переключается в redirect-режим;
- не использует новые таблицы;
- продолжает обслуживать свои брони независимо.

## Acceptance criteria

- `Поддержка` отсутствует в четырёх основных клиентских вкладках;
- `Бронь стола` открывается из основной навигации;
- поддержка доступна через дополнительное меню;
- свободное время считается backend;
- два одновременных запроса не занимают один стол;
- один пользователь не создаёт две будущие активные брони;
- клиент и ADMIN могут отменить бронь;
- ADMIN видит ближайшие брони;
- основной бот открывает экран бронирования;
- старый `restobot.service` остаётся запущен и не изменён.
