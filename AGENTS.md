# Инструкции coding-агенту

## Перед началом работы

1. Полностью прочитай `docs/00_MASTER_SPEC.md`.
2. Полностью прочитай файл этапа, который назвал пользователь.
3. Выполняй только текущий этап. Не начинай следующий без команды.
4. `PLAN_v1.md` — архив идей, а не актуальное ТЗ.

## Главный принцип проекта

Это один небольшой ресторан, один курьер и не более примерно 50 заказов в
день. Нужна простая, надёжная и удобная система. Не добавляй инфраструктуру и
функции «на будущее», если они прямо не указаны в актуальном ТЗ.

## Не усложнять

- Один Go backend, одна PostgreSQL, один VPS.
- Без микросервисов, Kubernetes, Redis, WebSocket/SSE и отдельного data
  warehouse.
- Интерфейсы обновляются обычным polling: кухня/курьер примерно раз в 5 секунд,
  клиент примерно раз в 10 секунд.
- Не добавлять геокодер, координаты, delivery zones и автоматическую
  маршрутизацию.
- Не добавлять склад, ингредиентные остатки и автоматическое списание.
- Не добавлять размеры, варианты, modifier groups и сложный конструктор блюда:
  у блюда есть только количество и необязательный комментарий к заказу.
- Не добавлять промокоды, бонусы, лояльность, чаевые и предзаказы.
- Не добавлять филиалы, courier claim, распределение курьеров и оптимизацию
  маршрутов: курьер один.
- На кухне не должно быть принятия заказа и нового business-status
  `PREPARING`. Допустима отдельная nullable-отметка `kitchen_started_at`:
  свайп `НОВЫЕ → В ПРОЦЕССЕ` только организует экран кухни. Основная кнопка —
  `ЗАКАЗ ГОТОВ`.

## Обязательные правила корректности

- PostgreSQL — источник истины для заказов, цен, статусов и платежей.
- Frontend никогда не задаёт итоговую цену и не меняет status произвольным
  значением.
- Деньги — integer minimal units, не `float`.
- В order items сохраняется снимок названия, цены, количества и суммы.
- Создание заказа защищено явным `Idempotency-Key` и unique constraint.
- Оплата подтверждается только проверенным webhook/server query, не страницей
  `success`.
- Telegram user доверяется только после серверной проверки raw `initData`.
- Сессия не хранится в `localStorage`.
- Телефон, адрес, токены, webhook secrets и raw `initData` не попадают в логи.
- Удаление блюда, которое уже встречалось в заказах, означает archive, а не
  физическое удаление истории.
- Редкие действия помещаются в меню `⋯` либо в Admin, а не рядом с основной
  кнопкой сотрудника.

## Роли

Только четыре роли:

- `CLIENT`;
- `KITCHEN`;
- `COURIER`;
- `ADMIN`.

Дополнительные роли `MANAGER`, `SUPERADMIN` и сложная permission hierarchy не
нужны. Первый ADMIN добавляется безопасной CLI-командой/переменной окружения,
дальше ADMIN управляет списком сотрудников.

Для локальной разработки Telegram ID `1048084234` является owner/tester: seed
добавляет ему staff-доступы `ADMIN`, `KITCHEN` и `COURIER`. Это не новая роль;
session выбирает одну активную роль из разрешённых backend.

## Основной автомат заказа

`NEW → OUT_FOR_DELIVERY → DELIVERED`

- `NEW` создаётся автоматически для cash-заказа или после подтверждения
  онлайн-оплаты.
- Kitchen ничего не принимает. Заказ сразу появляется в списке.
- Kitchen нажимает `ЗАКАЗ ГОТОВ`: backend атомарно ставит
  `OUT_FOR_DELIVERY` и создаёт уведомления клиенту и курьеру.
- Courier нажимает `ДОСТАВЛЕНО`: backend ставит `DELIVERED`.
- Внутренняя пометка `courier_started_at` делит экран курьера на `ОТВЕЗТИ` и
  `ВЕЗУ СЕЙЧАС`, но не является новым статусом, assignment или уведомлением
  клиенту.
- `CANCELLED` доступен только ADMIN с обязательной причиной.

Не вводи `PREPARING` в `fulfillment_status`, assignment или claim.
`READY_FOR_PICKUP` используется только для готового самовывоза.

## Проверка перед сдачей этапа

- Выполнены acceptance criteria файла этапа.
- Format, lint, typecheck и относящиеся к этапу тесты проходят.
- Миграции применяются на чистой PostgreSQL.
- OpenAPI и generated frontend types совпадают.
- Новые настройки описаны в `.env.example` без секретов.
- Проверены роли и невозможность прочитать чужой заказ.
- Обновлена документация запуска, если команды изменились.
- В отчёте перечислены изменённые файлы, проверки и оставшиеся ручные действия.
